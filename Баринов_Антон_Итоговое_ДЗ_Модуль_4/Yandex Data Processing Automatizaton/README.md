### Результаты выполнения Задания 2. Автоматизация работы с Yandex Data Processing при помощи Apache AirFlow

### 1. Выполненные действия
Развёрнуты сервисы:
- Managed Service for Apache Airflow;
- кластер Hive Metastore;
- кластер Data Proc (создаётся динамически через DAG);
- бакет Object Storage для хранения данных и артефактов;
- сетевая инфраструктура (сеть, подсеть, NAT-шлюз).

Создан и настроен сервисный аккаунт с ролями: editor, viewer, dataproc.agent, dataproc.editor, storage.editor, storage.viewer, storage.uploader, iam.serviceAccounts.user, managed-airflow.integrationProvider.

Реализован DAG, обеспечивающий:
- создание временного кластера Data Proc;
- запуск PySpark-задачи;
- автоматическое удаление кластера.

PySpark-скрипт протестирован вручную на мастер-ноде с использованием spark-submit. Скрипт работоспособен, так как данные читаются из CSV, преобразования выполняются, результат сохраняется.

### 2. Работоспособные компоненты
- DAG успешно создаёт и удаляет кластер Data Proc;
- Airflow имеет доступ к API Yandex Cloud;
- Сервисный аккаунт проходит авторизацию и обладает необходимыми правами;
- PySpark-скрипт полностью работоспособен при ручном запуске.

### 3. Зафиксированные ошибки
3.1. Ошибка выполнения PySpark-задачи через Airflow
При запуске задачи через DataprocCreatePysparkJobOperator возникает ошибка:
```Error code: 2. Details: []. Message: Unknown error```

Кластер создаётся, задание отправляется, но не выполняется.

3.2. Диагностика через YARN UI
YARN UI не содержит информации о задании: все категории (Running, Finished, Failed и др.) пусты. Веб-интерфейсы компонентов кластера недоступны.

3.3. Отсутствие логов в стандартных механизмах
Команды yc dataproc job log и yc logging read не возвращают данных по job_id. Логи задания в ожидаемых местах отсутствуют.

3.4. Обнаруженная ошибка в Cloud Logging
В логах кластера присутствует одна запись уровня ERROR:
```failed to read pidfile "/run/dataproc-agent.pid": open /run/dataproc-agent.pid: no such file or directory```

### 4. Исключённые возможные причины
- Права сервисного аккаунта	- соответствуют требованиям, прописанным в официальных документациях Yandex Cloud;
- Доступ к S3 (чтение скрипта и данных)	- работает при ручном запуске;
- Доступ к Hive Metastore (порт 9083) - сеть общая, доступ обеспечен;
- Работоспособность PySpark-скрипта - подтверждена ручным запуском;
- Версии образа Data Proc	Проверены версии 2.0, 2.1, 2.2, 2.3.

### 5. Основные выводы
- Кластер Data Proc, создаваемый через Airflow, не может корректно инициализировать собственный управляющий процесс (dataproc-agent);
- Следствием является невозможность выполнения заданий и отсутствие диагностической информации в штатных инструментах (YARN UI, yc job log, Cloud Logging);
- Проблема не связана с содержимым PySpark-скрипта и относится к конфигурации или окружению создаваемого кластера.

### 6. Нерешённые задачи
- Запуск PySpark-задачи через Airflow не был завершён успешно;
- Получение содержательного сообщения об ошибке от кластера Data Proc не обеспечено.

### 7. Результаты ручного тестирования
В связи с невозможностью запуска PySpark-задания через AirFlow было проведено ручное тестирование на мастер-ноде кластера Data Proc, созданного тем же DAG файлом. 
Тестирование подтвердило полную работоспособность кластера и скрипта:

7.1. Подключение к мастер-ноде по SSH
Подключение выполнено успешно с использованием SSH-ключа, указанного при создании кластера.
Команда: ```ssh ubuntu@<FQDN_мастера>```

7.2. Проверка доступности Object Storage
Выполнена команда hdfs dfs -ls s3a://bank-credits-bucket/
Результат: бакет доступен, все файлы и папки видны:
```
text
Found 4 items
-rw-rw-rw-   credit_applications.csv   57362384 bytes
drwxrwxrwx   dags/
drwxrwxrwx   dataproc/
drwxrwxrwx   scripts/
```

7.3. Запуск тестового PySpark-скрипта локально
Создан минимальный скрипт /tmp/test.py с выводом версии Spark
Команда: ```spark-submit --master local[*] /tmp/test.py```

7.4. Запуск полного PySpark-скрипта локально
Скрипт create-table.py с master("local[*]") читает CSV из S3, выполняет трансформации (приведение типов, агрегация), сохраняет результат в Parquet
Команда: ```spark-submit --master local[*] /tmp/process_data.py```
Результат: Данные были успешно прочитаны, агрегация выполнена корректно, вывод сохранён в s3a://bank-credits-bucket/output/

7.5. Вывод по ручному тестированию
- Кластер Data Proc полностью функционален;
- Spark 3.3.2 работает как в локальном режиме (local[*]), так и с доступом к S3;
- PySpark-скрипт корректен и выполняет все требуемые трансформации;
- Проблема: отказ происходит на уровне API-взаимодействия AirFlow и Data Proc, а не на уровне кластера или скрипта.
